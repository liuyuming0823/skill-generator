# 从需求生成技能 · 设计指南

体检脚本管的是「合规」，本文件管的是「好不好用」。前者能自动跑，后者要靠判断。

---

## 1. 先定形态，再动手

同一个需求可能有多种实现形态，选错形态的代价是维护成本翻倍。

| 形态 | 判据 | 落点 | 反例（选错的样子） |
|---|---|---|---|
| **纯指导型** | 以判断、话术、流程约定为主，没有必须精确复现的命令 | 只有 `SKILL.md`，长内容拆 `references/` | 给"写周报的语气要求"写了个 Python 脚本 |
| **脚本型** | 有固定命令序列、数据处理、外部 API 调用 | `scripts/` + 正文写清调用方式与参数 | 让模型每次现场拼 SQL 查询，第三次就漂了 |
| **模板型** | 反复产出同一形态的东西（报告、卡片、页面、周报） | `templates/` 放可复制骨架 | 把模板内容写死在 SKILL.md 正文里，改一次要翻全文 |
| **混合型** | 上面两种以上并存（大多数真实技能） | 目录齐全，正文分节说明每块用途 | 全部塞进 SKILL.md，两万字符后没人看得懂 |

两条硬判据：

- **能用一句祈使句说清的流程，不要写脚本。** 脚本是维护负担，改一次要重新体检、重新分发。
- **需要精确复现的必须写脚本。** 例如"按固定规则解析字段""按固定格式生成文件"——靠模型临场发挥，结果每次都不一样。

## 2. `description` 怎么写

`description` 是**给模型看的**，它决定这个技能什么时候被加载。写坏了两条后果：该触发时不触发，不该触发时乱触发。

| 写法 | 例子 | 问题 |
|---|---|---|
| ❌ 只写名词 | `description: 待办查询工具` | 没有触发场景，模型不知道何时用 |
| ❌ 书面语触发词 | `description: 获取待办事项列表数据` | 用户不会这么说话 |
| ❌ 塞满功能清单 | `description: 支持查询、导出、重试、清理、统计…` | 触发场景被稀释 |
| ✅ 三件事齐备 | `无头登录 OA 拉取待办列表，不碰审批详情页。当用户说「查待办」「OA 待办」「今天有什么要审的」时使用。` | — |

**三件事**：① 做什么（一句话）② 边界（不做什么，避免误触发）③ 触发词（用户的原话）。

补充两条：

- **中英文各一份要真写**。`description_zh` 不是 `description` 的复制粘贴，它是给人在市场列表里看的，30 字以内说清价值。
- **不要出现 `<` `>`**。市场校验会直接失败。占位符一律用方括号或中文书名号。

## 3. 触发词怎么提炼

写触发词时把这句话念一遍：**"用户会怎么开口？"** 别写你想让他怎么说。

| 场景 | 差的触发词 | 好的触发词 |
|---|---|---|
| OA 待办 | 待办事项查询 | 查待办、OA 待办、今天要审什么 |
| 视频字幕 | 视频语音合成处理 | 加字幕、配音、给视频配个音 |
| 技能生成 | 技能封装与分发 | 做个技能、把这个存成技能、打包技能 |
| 标书分析 | 招投标文件评审 | 标书分析、这份标书能不能投 |

技巧：

- 收 3~6 个：覆盖主要说法，别贪多
- 中英文混排的识别场景，把英文说法也收上（`package skill`、`create skill`）
- 同一句话的不同省略形式都收（"查待办" / "查下待办" / "看看待办"）
- 触发词写进 `trigger:` 结构化字段（比正文散文更稳），同时确保它们出现在 `description` 里

## 4. 内容该放哪一层

分层的唯一目的是**控制上下文开销**：SKILL.md 每次触发都会被读，`references/` 按需读，`scripts/` 只读命令不读实现。

| 内容 | 落点 | 判据 |
|---|---|---|
| 触发条件、执行流程、步骤骨架 | `SKILL.md` 正文 | 每次执行都要看 |
| 字段类型表、API 字段定义、错误码表 | `references/` | 只在某一步需要 |
| 领域知识、行业规则、判定标准 | `references/` | 长，且不是每次都用 |
| 踩坑记录 | `SKILL.md` 的「常见坑」 | 短就留正文；超过 10 条拆到 `references/` 下单独一份文档（如排错笔记） |
| 可执行逻辑、数据处理、外部调用 | `scripts/` | 需要精确复现 |
| 依赖安装、首次配置向导 | `scripts/setup.py` | 有第三方依赖就必须有 |
| 报告/卡片/页面骨架 | `templates/` | 反复产出的同一形态 |
| 图片、字体、样板稿 | `assets/` | 参与产出但不需读进上下文 |
| 配置字段说明 | `config/*.example.json` | 字段留全、值留空 |
| 运行产物（日志、缓存、输出文件） | **不入包** | 使用者本机生成 |

阈值参考：`SKILL.md` 超 15000 字符就该考虑拆；超 30000 字符体检会直接报警。

**引用只写真存在的文件。** 体检会逐条验路径，写了不存在的会被判「引用缺失」P1；确实是运行时产物的，正文里显式写成「输出文件 `xxx.json`」。

## 5. 生成前的澄清话术

**默认不问。** 能从上下文推断的就按默认走，并在回复里注明假设。确实需要问时，一次问清、给选项，别开放式提问：

| 该问的 | 话术 |
|---|---|
| 触发场景 | "你希望用户说什么话时触发它？给两三个说法就行。" |
| 输入输出 | "它读什么、产出什么？是文件、链接，还是纯文本？" |
| 作用域 | "只你自己用，还是要给同事／上架市场？" |
| 外部依赖 | "要连的账号或外部程序有哪些？我先按无凭据设计。" |

不该问的：技能叫什么名字（可以从用途推）、用什么语言写（跟着项目走）、要不要版本号（默认给）。

## 6. 生成后自检（8 项）

生成完把这份清单过一遍，再交给用户：

1. `name` 是 kebab-case，且与目录名一致
2. `description` 三件事齐备（做什么 / 边界 / 触发词），无尖括号
3. `description_zh` / `description_en` 是**另行撰写**的，不是复制粘贴
4. 正文里的 `<...>` 占位**全部替换**，一个不剩
5. 正文提到的每个文件都真实存在（运行时产物已显式标注）
6. 有第三方依赖 → 有 `scripts/setup.py`；有配置 → 有 `config/*.example.json`
7. 「常见坑」写了 ≥1 条真实踩过的坑
8. `python scripts/audit_skill.py <技能目录> --market` 输出 P0=0 P1=0

前 3 项和 8 项体检能兜住，4~7 项只能人工过。

## 7. 一个完整例子

需求原话：**"我想有个技能，能自动把我写的那些视频文案变成带字幕的视频。"**

**澄清**（只问必要的）：触发词是"加字幕"还是"配音"？输入是文案 JSON 还是 Word？（结果：两者都要支持）

**定形态**：有固定命令序列（合成视频）+ 反复产出同一形态（每条视频的文案模板）→ **混合型**，要 `scripts/` + `templates/` + `references/`（编码与踩坑表）。

**建骨架**：

```bash
python scripts/new_skill.py daily-grind-video \
    --display-name 打工人吐槽视频 \
    --desc "把文案 JSON 合成竖屏短视频（AI 配音 + 同步字幕）。当用户说「做视频」「加字幕」「配音」时使用。" \
    --desc-zh "文案一键合成竖屏带字幕配音短视频" \
    --desc-en "Turn a copy JSON into a vertical short video with AI voice and synced subtitles" \
    --triggers 做视频,加字幕,配音,生成短视频 \
    --dirs scripts,references,templates --deps edge-tts,moviepy
```

**填内容**：`scripts/` 放合成脚本；`references/` 放字体回退与编码踩坑（`TextClip` 中文裁切、`remove_temp=False`）；`templates/` 放文案 JSON 骨架；正文写清"哪一步检查依赖、哪一步会失败、失败怎么办"。

**脱敏**：字体路径改成候选列表 + 探测函数，不写死盘符；`output/` 与 `assets/` 里的成品不进包。

**交付**：体检 0/0 → 打包（默认按市场规范）→ `--install` 装到本机。
